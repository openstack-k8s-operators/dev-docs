# Service Runtime Architecture (post-kolla)

This document describes how OpenStack services run after the removal of the
kolla entrypoint pattern. It complements
[service_config.md](service_config.md), which covers how configuration files
are generated; this document covers how they are mounted and how services
execute at runtime.

## What Changed

Previously, every service container started via `/usr/local/bin/kolla_start`,
which ran `kolla_set_configs` to copy config files from a staging directory
(`/var/lib/config-data/default`) to their final locations (e.g.
`/etc/keystone/keystone.conf.d/`), chowning them to the service user in the
process. This required the `anyuid` SCC (Security Context Constraint) and
`sudo` inside the container.

Now, services use **direct SubPath volume mounts** to place config files at
their final paths, and execute the service binary directly — no kolla scripts,
no privilege escalation, no root.

## Service Identity

Each OpenStack service has a dedicated, image-baked UID/GID defined in
`lib-common/modules/users`. The registry is the single source of truth
for both Go operators (via constants like `users.KeystoneUID`) and TCIB
container image builds (via `zz_generated_uid_gid.yaml`, regenerated by
`make generate-uids-gids`).

The full list of users, UIDs, GIDs, home directories, and supplemental groups
is in
[`modules/users/registry.go`](https://github.com/openstack-k8s-operators/lib-common/blob/main/modules/users/registry.go)
(the `Registry` map and the const block above it). The generated YAML
consumed by container image builds is `zz_generated_uid_gid.yaml` in the
same directory.

The `ApacheGID` (48) may be added as a supplemental group for httpd-fronted
services — see the SecurityContext section below.

## SecurityContext

All workloads use helpers from `lib-common/modules/common/pod`:

### Pod level

```go
pod.RestrictivePodSecurityContext(users.<Service>UID, users.<Service>GID, supplementalGroups...)
```

Sets `RunAsUser` to the service UID, `RunAsGroup` and `FSGroup` to the service
GID, `RunAsNonRoot: true`, seccomp `RuntimeDefault`. The optional
`supplementalGroups` parameter grants additional GIDs — most commonly
`users.ApacheGID` (see below).

### Container level

```go
pod.RestrictiveSecurityContext(users.<Service>UID, users.<Service>GID, addCapabilities...)
```

Sets `RunAsUser` to the service UID, `RunAsGroup` to the service GID,
`RunAsNonRoot: true`, drops ALL capabilities (then adds back any explicitly
requested), disables privilege escalation, seccomp `RuntimeDefault`.

### Privileged containers

```go
pod.PrivilegedSecurityContext(users.<Service>UID, users.<Service>GID)
```

For workloads needing full host device access (e.g. glance/cinder with Ceph
RBD backends via os-brick's nsenter shim). `RunAsNonRoot` is only set when the
UID is non-zero.

### Apache supplemental group

httpd-fronted services might need `users.ApacheGID` as a supplemental group,
depending on which httpd addon modules are installed and the ownership /
permissions of the config files they ship. The supplemental group is the third
argument to `RestrictivePodSecurityContext` (the second argument is the
`RunAsGroup`/`FSGroup`):

```go
pod.RestrictivePodSecurityContext(users.KeystoneUID, users.KeystoneGID, users.ApacheGID)
```

This is required when RPM-shipped httpd conf.d files are baked into the image
with `root:apache 0640` ownership -- for example `mod_auth_openidc`'s
`auth_openidc.conf`, which keystone needs for federation. Without the apache
group, the non-root service user cannot read them.

Horizon is a special case: its httpd workers always ran as `apache` under
kolla (never a dedicated service user), so it uses `users.ApacheUID` as the
pod's **primary** user identity rather than adding apache as a supplemental
group:

```go
pod.RestrictivePodSecurityContext(users.ApacheUID, users.HorizonGID)
```

### Mixed-privilege pods

Some pods contain both non-root and root containers. The pod-level
`RestrictivePodSecurityContext` sets the non-root default; containers that
genuinely need root override it:

```go
SecurityContext: &corev1.SecurityContext{
    RunAsUser:    ptr.To(int64(0)),
    RunAsNonRoot: ptr.To(false),
    Capabilities: &corev1.Capabilities{
        Add: []corev1.Capability{"NET_ADMIN", "NET_RAW"},
    },
},
```

Examples:
- **ironic**: `dnsmasq` needs root for DHCP on privileged ports; `pxe-init`
  runs as root but drops `ALL` and adds back only `DAC_OVERRIDE` (write into
  the fsGroup-owned `var-lib-ironic` emptyDir), `FOWNER` (chmod shared assets
  it does not own), and `SYS_CHROOT`/`SETFCAP` (chroot-based CA-cert patch);
  `SYS_ADMIN` is deliberately not granted
- **designate**: `unbound` runs as root (DNS on port 53)

### AutomountServiceAccountToken

Set `AutomountServiceAccountToken: ptr.To(false)` on workloads whose
containers do not access the Kubernetes API. This is the case for all
OpenStack service operators migrated so far — `ServiceAccountName` is kept
only for SCC binding, not for in-pod API access.

However, some operators (e.g. infra-operator, mariadb-operator) have scripts
that connect to the Kubernetes API from within containers. Those workloads
must keep `AutomountServiceAccountToken` enabled (the default). Check the
operator's templates/scripts before disabling it.

Note: DownwardAPI volumes (e.g. ironic's `k8s.v1.cni.cncf.io/network-status`
annotation projection) do not require the token — they are projected by the
kubelet from local pod metadata, not fetched from the API server.

## SCC (Security Context Constraints)

The target SCC is `nonroot-v2` for most services. Operators that need elevated
SCCs request them alongside `nonroot-v2` in both the kubebuilder RBAC marker
and the `rbacRules` slice:

| SCC | Operators | Reason |
|-----|-----------|--------|
| `nonroot-v2` only | keystone, heat, neutron, watcher, nova, placement, cyborg, horizon | Standard non-root |
| `nonroot-v2` + `privileged` | cinder | Ceph RBD host device access via os-brick |
| `nonroot-v2` + `privileged` + `hostmount-anyuid` | glance | Ceph RBD host device access via os-brick (privileged); NFS backend host mounts (hostmount-anyuid) |
| `nonroot-v2` + `anyuid` + `privileged` | octavia, designate, ironic | dnsmasq root (ironic), unbound root (designate), amphora management (octavia) |
| `nonroot-v2` + `anyuid` | barbican | PKCS11/HSM prep job needs root for vendor client library setup |
| `nonroot-v2` + `hostmount-anyuid` | manila | Share driver host mounts |

Even when an operator's RBAC grants access to an elevated SCC (e.g.
`hostmount-anyuid`), pods that don't actually need it will still be admitted
under `nonroot-v2` — OpenShift's SCC admission selects the most restrictive
SCC that satisfies the pod's SecurityContext, not the most permissive one the
ServiceAccount is allowed to use.

## Config Mounting

### DefaultMode

All config Secret volumes use `DefaultMode: 0440` (owner-read + group-read).
This is the most restrictive mode that works — every SubPath mount is
`ReadOnly: true`, so no service needs write permission on config files.

### Mounting strategies

Three patterns exist, from simplest to most complex:

**1. Direct SubPath mounts** (most services):

Config files are mounted directly from the Secret to their final path:

```go
{Name: "config-data", MountPath: "/etc/keystone/keystone.conf.d/00-default.conf",
 SubPath: "00-default.conf", ReadOnly: true}
```

Used by: keystone, glance, neutron, watcher, cyborg, ironic-neutron-agent.

**2. conf.d directory mount** (oslo.config services with config-dir):

The entire Secret is mounted as a directory at the service's `conf.d` path.
The service discovers config files via oslo.config's `--config-dir` argument:

```
Command: []string{"cinder-scheduler"}
Args:    []string{"--config-dir", "/etc/cinder/cinder.conf.d"}
```

Used by: cinder, manila, heat, barbican.

**3. Init-container merge** (services needing runtime config merging):

An init container uses `crudini` to merge base + overwrite configs into an
EmptyDir, which the main container then reads:

Used by: octavia, designate (shared components), ironic (conductor).

### TLS certificate paths

After removing kolla's config.json staging, `svc.CertMount` and `svc.KeyMount`
must be set to the final paths before calling `svc.CreateVolumeMounts()`:

```go
certMount := fmt.Sprintf("/etc/pki/tls/certs/%s.crt", endpt.String())
keyMount := fmt.Sprintf("/etc/pki/tls/private/%s.key", endpt.String())
svc.CertMount = &certMount
svc.KeyMount = &keyMount
```

Without this, lib-common defaults to its staging path
(`/var/lib/config-data/tls/...`), which nothing copies from once kolla is gone.

## Writable Paths

Non-root containers cannot write to image-baked directories owned by root.
EmptyDir volumes provide writable paths where needed.

`lib-common/modules/common/volume` provides generic helpers:

```go
volume.WritableDirVolume(name string, sizeLimit ...*resource.Quantity) corev1.Volume
volume.WritableDirVolumeMount(name, mountPath string) corev1.VolumeMount
volume.WritableDirSubPathMounts(volumeName, baseDir string, subdirs ...string) []corev1.VolumeMount
volume.ConfigSecretVolumes(secretNames []string) ([]corev1.Volume, []corev1.VolumeMount)
```

### Well-known constants

| Constant | Value | Purpose |
|----------|-------|---------|
| `volume.RunHttpdVolumeName` | `"run-httpd"` | Volume name for httpd PID directory |
| `volume.RunHttpdMountPath` | `"/run/httpd"` | Canonical mount path (not `/etc/httpd/run`) |
| `volume.VarLogHttpdVolumeName` | `"var-log-httpd"` | Volume name for httpd log directory |
| `volume.VarLogHttpdMountPath` | `"/var/log/httpd"` | Image ships this as root:root 0700 |
| `volume.TmpVolumeName` | `"tmp"` | Volume name for /tmp |
| `volume.TmpMountPath` | `"/tmp"` | oslo_concurrency lock_path, tooz state |
| `volume.HomeDirCacheSubdir` | `".cache"` | RHEL pkg_resources entry-point cache subdir |

Usage:

```go
volumes = append(volumes,
    volume.WritableDirVolume(volume.RunHttpdVolumeName),
    volume.WritableDirVolume(volume.VarLogHttpdVolumeName),
    volume.WritableDirVolume(volume.TmpVolumeName),
)
volumeMounts = append(volumeMounts,
    volume.WritableDirVolumeMount(volume.RunHttpdVolumeName, volume.RunHttpdMountPath),
    volume.WritableDirVolumeMount(volume.VarLogHttpdVolumeName, volume.VarLogHttpdMountPath),
    volume.WritableDirVolumeMount(volume.TmpVolumeName, volume.TmpMountPath),
)
```

### Service-specific emptyDir volumes

These use `volume.WritableDirVolume("name")` with string literals — no
constants, since they're per-operator:

- `/var/log/<service>` — service logs for the log-streaming sidecar pattern
  (`tail -n+1 -F <logfile>`)
- Service home subdirs — use `volume.WritableDirSubPathMounts()` for
  writable subdirs (e.g. `.cache`, `tmp`, `groups`) without shadowing the
  entire home directory

### httpd.conf adjustments

When httpd runs as a non-root service user instead of the `apache` user:

- `User <service>` / `Group <service>` — if the service's
  `WSGIDaemonProcess` already declares `user=<service> group=<service>`,
  that proves a dedicated system user exists in the image; change to match.
  Otherwise keep `User apache` (e.g. horizon, ironic-inspector's proxy httpd).
- `PidFile /run/httpd/httpd.pid` — explicit, since the default may resolve
  to an unwritable path
- Top-level `ErrorLog /dev/stderr` — prevents fallback to Apache's compiled-in
  default `logs/error_log` (relative to ServerRoot, which resolves to the
  unwritable `/var/log/httpd/error_log`)

## Service Commands

Direct exec, no shell wrapper needed:

| Workload type | Command pattern |
|---------------|----------------|
| httpd-fronted API | `/usr/sbin/httpd -DFOREGROUND` |
| RPC/worker service | `<service>-<component> --config-dir /etc/<service>/<service>.conf.d` |
| DB sync | `<service>-manage db sync` or `<service>-dbsync --config-dir ... upgrade` |
| Log sidecar | `/usr/bin/dumb-init --single-child -- /usr/bin/tail -n+1 -F <logpath>` |
| DB purge cronjob | `/bin/bash <script-mount-path>/dbpurge.sh` |

## Operator-Specific Notes

### glance

- `workerSelfReferenceScript`: when `GLANCE_DOMAIN` is set (distributed image
  import), each replica writes a runtime-only `01-config.conf` into the conf.d
  directory at container start — the pod's hostname isn't known until then.
  This writes a NEW file into the container's own directory, not into a
  Secret-mounted file, so DefaultMode 0440 is unaffected.
- Ceph backends: `pod.PrivilegedSecurityContext` for os-brick host device
  access via `nsenter`.

### ironic

- Mixed-privilege pods: `dnsmasq` (root + `NET_ADMIN`/`NET_RAW`) and
  `pxe-init` (root, drops `ALL`, adds back
  `DAC_OVERRIDE`/`FOWNER`/`SYS_CHROOT`/`SETFCAP`) use per-container
  SecurityContext overrides.
- Shared ServiceAccount: all CRDs (IronicAPI, IronicConductor,
  IronicInspector, IronicNeutronAgent) resolve `RbacResourceName()` to the
  same string when owned by a parent `Ironic` CR, so they share one Role and
  cannot get independently different SCC grants.
- `DownwardAPI` volume for `network-status` annotation (predictable IPs).

### horizon

- 3-init-container pipeline: `secret-setup` → `theme-setup` →
  `dashboard-setup`. The `dashboard-setup` container invokes the image's
  `kolla_extend_start` script (stripped of its httpd-launch tail line) to
  enable dashboard panels and regenerate Django static assets.
- Uses `ConfigMap` for config data (not Secret).
- Uses `ApacheUID` as the primary UID (not `HorizonUID`), with `HorizonGID`
  as the `RunAsGroup`/`FSGroup`. No apache supplemental group is needed since
  the pod already runs as the apache user.

### barbican

- HSM/PKCS11 volumes for hardware security module client data.
- PKCS11 prep job runs as root (`anyuid` SCC) — vendor client library setup
  hasn't been verified under non-root without real HSM hardware.

### designate

- `ProcessVolumes` / `VolumeMapping` abstraction for complex volume routing.
- `bind9` backend has its own fully separate volume scheme with TSIG/RNDC keys.
- `unbound` runs as root (DNS on port 53), uses per-container SecurityContext
  override on top of pod-level `RestrictivePodSecurityContext`.

### swift

- Already kolla-free before this effort — different architecture using
  `ProjectedVolumeSource` combining secrets and configmaps.
